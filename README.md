# SRS: language-learning tools

Prototype suite of spaced-repetition (SRS) language-learning tools. The first
tool is a **typed-recall vocabulary trainer**: it introduces new words, has you
type each one, then schedules reviews with [FSRS](https://github.com/open-spaced-repetition/ts-fsrs).

See [`docs/decisions.md`](docs/decisions.md) for why things are the way they are.

## Stack

| Layer      | Choice                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime    | Node 24 LTS (runs `.ts` natively via type stripping), pnpm workspaces + Turborepo                                                           |
| Database   | Postgres 18 (Docker Compose locally)                                                                                                        |
| Schema     | [Atlas](https://atlasgo.io): declarative `db/schema.sql` → versioned migrations in `db/migrations`                                          |
| API        | Fastify 5 + `fastify-type-provider-zod`, Kysely (types generated by `kysely-codegen`), OpenAPI at `/docs`                                   |
| Web        | Next.js 16 (App Router), Tailwind 4, shadcn/ui (Base UI)                                                                                    |
| Mobile     | Expo SDK 58 (React Native 0.88), minimal for now: shell and course list (dev auth); Jest + React Native Testing Library                     |
| Client     | `@app/client`: per-screen controllers and view models, TanStack Query core, MSW fake API ([ADR 0002](docs/adr/0002-client-architecture.md)) |
| Shared     | `@app/shared`: Zod contracts + answer grading, used by both sides                                                                           |
| Scheduling | `ts-fsrs` v6 (FSRS-7 model)                                                                                                                 |
| Tooling    | TypeScript 6, Biome (lint + format), Vitest, GitHub Actions                                                                                 |

## Layout

```

apps/web         Next.js app: src/app (routes), src/views (views + screens), src/platform, src/components/ui
apps/mobile      Expo app: src/app (root + router), src/views (views + screens), src/platform (ports, theme)
packages/client  Controllers, view models, API client, React binding, testing kit (shared with mobile)
packages/design  Design system: tokens.json (one source for web and mobile), generators, system docs
apps/e2e         Playwright tests: pages/ (page objects), tests/ (specs), support/ (fixtures)
packages/shared  Zod contracts + grading (imported as TS source)
db/schema.sql    Desired schema (edit this)
db/migrations    Generated, committed migrations (never edit)
db/seed          Sample course CSV (local databases only)
db/courses       Prebuilt course CSVs (every environment; apps/api/src/db/prebuilt.ts)
db/rehearsal     Production-shaped data generator and invariants for the migration rehearsal
scripts/verify/  `pnpm verify`: change classes and verification rules (rules.ts), runner
scripts/         setup-agent-env.sh (cloud session setup), db-check.sh (CI schema guard),
                 check-commit-messages.sh (no session links)
.githooks/       pre-commit (Biome), commit-msg and pre-push guards, enabled by `pnpm install`
docs/            decisions.md, verification.md, adr/
```

## Getting started

Prerequisites: Node 24 (`.nvmrc`), pnpm 10 (`corepack enable`), Docker, and the
[Atlas CLI](https://atlasgo.io/getting-started#installation)
(`curl -sSf https://atlasgo.sh | ATLAS_VERSION=v1.3.8 sh`, the version CI pins),
and [oasdiff](https://github.com/oasdiff/oasdiff) v1.34.1 for the
`openapi-breaking` check.

```sh
cp .env.example .env
pnpm install
pnpm db:setup        # start Postgres 18, apply migrations, seed the courses
pnpm dev             # API on :4000 (docs at /docs), web on :3000
```

Claude Code cloud sessions set all of this up automatically through a
SessionStart hook; see `scripts/setup-agent-env.sh`, which also works by hand
on a Linux machine where you are root. It also installs the Neon CLI and
pulls the deployed database's connection strings into the git-ignored
`.env.neon` (with `NEON_API_KEY` set, or in a cloud session whose environment
holds the key); without a key it skips that step.

## Common tasks

| Command                                        | What it does                                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| `pnpm dev`                                     | Run API and web in watch mode                                                         |
| `pnpm verify` / `pnpm verify plan`             | Run / show the checks this diff requires (see `docs/verification.md`)                 |
| `pnpm test`                                    | All tests (API tests use `TEST_DATABASE_URL`; Postgres must be running)               |
| `pnpm e2e`                                     | Playwright browser tests (starts API + web unless already running; needs a seeded DB) |
| `pnpm e2e:scratch [file]`                      | Throwaway specs in `apps/e2e/scratch/` (git-ignored, never in CI); see its README     |
| `pnpm typecheck` / `pnpm lint` / `pnpm format` | Types, Biome check, Biome autofix                                                     |
| `pnpm db:diff <name>`                          | After editing `db/schema.sql`: generate a migration                                   |
| `pnpm db:migrate`                              | Apply pending migrations to `DATABASE_URL`                                            |
| `pnpm db:codegen`                              | Regenerate `apps/api/src/db/types.ts` from the migrated DB                            |
| `pnpm db:check`                                | Validate migrations and confirm they match `schema.sql` (runs in CI)                  |
| `pnpm db:lint`                                 | Lint new migrations: Squawk and the expand/contract policy (ADR 0003)                 |
| `pnpm db:rehearse`                             | Apply new migrations to production-shaped data, timed, then check invariants          |
| `pnpm db:hash`                                 | Re-hash `atlas.sum` after editing a new, unapplied migration                          |
| `pnpm db:seed`                                 | Load the prebuilt courses and the sample course, once per database (idempotent)       |
| `pnpm api:openapi`                             | Regenerate the committed OpenAPI snapshot `apps/api/openapi.json`                     |
| `pnpm design:build`                            | Regenerate token files from `packages/design/tokens.json` (web CSS, native TS)        |
| `pnpm design:system`                           | Build the design-system artifact's files into `packages/design/.system/`              |
| `pnpm --filter @app/mobile start`              | Expo dev server for the mobile app (Expo Go or a simulator)                           |
| `pnpm --filter @app/mobile test`               | Mobile view and screen tests (Jest, React Native Testing Library, MSW fake API)       |
| `pnpm --filter @app/mobile preview:web`        | Export the mobile app through react-native-web, for screenshots without a device      |

First e2e run: `pnpm --filter @app/e2e exec playwright install chromium`, or set
`PLAYWRIGHT_CHROMIUM_EXECUTABLE` to an existing Chromium binary.

Schema change loop: edit `db/schema.sql` → `pnpm db:diff add_thing` →
`pnpm db:migrate` → `pnpm db:codegen` → commit all three.

## Sign-in (Auth0)

**Locally, nothing to set up.** The API defaults to `AUTH_MODE=dev`: every
request is the local learner (`dev|local`), or the user the `x-dev-user`
header names, which is how each e2e test gets a fresh learner. Without the
`NEXT_PUBLIC_AUTH0_*` variables the web uses a dev auth port: signed in as
"Local learner", no login, and "Sign out" shows the sign-in screen in memory
(either button signs back in). Tests and e2e never reach Auth0.

**Production** (Vercel) signs in through the Auth0 tenant
`hallavo.eu.auth0.com`: Google, or email and password, both on Auth0's
Universal Login page, invite-only. The web gets an access token for the
API (`@auth0/auth0-spa-js`, rotating refresh tokens) and sends it as
`Authorization: Bearer`; the API (`AUTH_MODE=jwt`) verifies it against the
tenant's JWKS and refuses to start on Vercel in dev mode.

| Project | Variable                             | Value                                                     |
| ------- | ------------------------------------ | --------------------------------------------------------- |
| API     | `AUTH_MODE`                          | `jwt`                                                     |
| API     | `AUTH0_DOMAIN`                       | `hallavo.eu.auth0.com`                                    |
| API     | `AUTH0_AUDIENCE`                     | `https://srs-technical-poc.vercel.app`                    |
| API     | `AUTH_LEGACY_OWNER_EMAIL` (optional) | The owner's email: their first sign-in keeps old progress |
| Web     | `NEXT_PUBLIC_AUTH0_DOMAIN`           | `hallavo.eu.auth0.com`                                    |
| Web     | `NEXT_PUBLIC_AUTH0_CLIENT_ID`        | `XH7eWzd8b4tJ0XD6ILTFTxu926BbYw5x`                        |
| Web     | `NEXT_PUBLIC_AUTH0_AUDIENCE`         | `https://srs-technical-poc.vercel.app`                    |

None of these are secrets. To try real sign-in locally, set the three web
variables in `.env` and run the API with the three API ones (the tenant
allows `http://localhost:3000`); an invited account is still needed. Mobile
keeps the dev auth port until its own sign-in (issue #48).

## Mobile app

`apps/mobile` is a minimal Expo app (decisions log, 2026-11-14): the shell
and the course list, over the same controllers and view models as the web.
It runs on the dev auth port, so it needs the API in dev mode. The full
app waits for a mobile design shared with the web app (issue #48).

```sh
pnpm dev                              # the API on :4000
pnpm --filter @app/mobile start       # then press i (iOS simulator) or a (Android emulator)
```

The app calls `EXPO_PUBLIC_API_URL`, default `http://localhost:4000`, which
the iOS simulator reaches. An Android emulator needs
`EXPO_PUBLIC_API_URL=http://10.0.2.2:4000`, a device the host's LAN
address.

## Importing words

Create a course, then paste or upload a CSV on its page:

```csv
unit,term,definition,alternatives,notes
Greetings,hola,hello,,
Around town,el ordenador,computer,la computadora|computadora,"Spain vs Latin America"
```

`term` is what the learner types (target language), `definition` is the prompt,
`alternatives` are other accepted answers separated by `|`.

For a quicker way in, the course page links to **Import words**
(`/courses/:id/import`): paste one word per line (term and definition
separated by a tab, a comma, " - " or " = "), or pick a Quizlet export or
an Anki "Notes in Plain Text" `.txt`. It previews the words and the
skipped lines before anything is imported. The parsers are in
`packages/shared/src/import-formats.ts`.

## Learning steps

A new word answered correctly is due again after 10 minutes, then after a
day, and FSRS schedules it from then on. A wrong answer during the steps
brings it back after 10 minutes and starts the steps over. To change the
waits, edit `LEARNING_STEPS` in `apps/api/src/learning-steps.ts`; the
scheduler (`apps/api/src/srs.ts`) reads it and needs no change. Cards already
on a step keep their step number and continue with the new waits.
