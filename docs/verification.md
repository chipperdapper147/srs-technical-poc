# Verification strategy

Goal: a clearly defined way to show, at every stage from first edit to
production, that a change works as intended and broke nothing else.

**Status:** stages 0–3 are in place and automated. Stages 4–7 are the target
state, blocked on a deploy target and Auth0 (see the bottom of this file).

## The rule

A change is sufficiently verified when **all three** hold:

1. **Checks:** every check its change classes require passes.
2. **Obligations:** every "this change needs a test" obligation is met by a
   test change in the same branch, or waived with a written reason.
3. **Manual evidence:** every evidence item (screenshots, a reviewed diff) is
   reported with the PR.

What a change requires is not a judgment call. `pnpm verify` diffs the branch
against `main`, puts each changed file in exactly one **change class**, and
takes the union of their requirements. The classes, checks and obligations are
data in [`scripts/verify/rules.ts`](../scripts/verify/rules.ts); the tables
below are generated from it, and CI fails if they drift apart.

Who enforces what:

| Part            | Locally                                                          | CI on a PR                                                   |
| --------------- | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| Checks          | `pnpm verify`, targeted to the diff                              | every check, full scope (`pnpm verify --all`, parallel jobs) |
| Obligations     | `pnpm verify`, and the pre-push hook                             | the `obligations` job                                        |
| Manual evidence | `pnpm verify` lists what's owed; the author or agent supplies it | the job summary lists it; the PR description carries it      |

Rules of thumb behind the classes:

- **Fail safe.** A file no class matches is `unclassified` and requires the
  full run. Dependencies, CI and tooling changes also require the full run.
- **Behaviour changes ship with a kept test** of the matching kind. Refactors
  and pure styling changes are the expected waivers.
- **Generated files are checked by regenerating them** (drift checks): Kysely
  types, the OpenAPI snapshot, and the tables in this file.
- **E2E is targeted locally, complete in CI.** The e2e map says which specs
  guard which source files; anything unmapped runs the whole suite.

### Running it

```sh
pnpm verify plan                 # what this change needs, and why
pnpm verify                      # run it and print the report
pnpm verify --all                # everything, whole e2e suite
pnpm verify --skip e2e="no browser in this sandbox"   # listed as skipped, still fails nothing
pnpm verify --waive api-test="pure rename"            # for uncommitted work
```

Waive an obligation in a commit with a trailer, so the reason travels with
the change and CI sees it:

```
Verify-Waive: e2e-spec: spacing-only change, covered by the visual check
```

An unknown id in a trailer fails the run, so a typo can't waive nothing.
`pnpm verify` needs Postgres (`pnpm db:setup`), Atlas and Docker for the
checks that use them; a missing dependency shows as **blocked**, not passed.

### Obligations

A class with an obligation must ship with a matching test change, or a
`Verify-Waive: <id>: <reason>` trailer on one of the branch's commits.

| Obligation                                                 | Met by a change to                       |
| ---------------------------------------------------------- | ---------------------------------------- |
| `api-test`: An API integration test is added or changed    | `apps/api/test/**`                       |
| `shared-test`: A shared unit test is added or changed      | `packages/shared/src/**/*.test.ts`       |
| `web-unit-test`: A web unit test is added or changed       | `apps/web/src/**/*.test.ts`              |
| `e2e-spec`: An e2e spec or page object is added or changed | `apps/e2e/tests/**`, `apps/e2e/pages/**` |

## Reporting rule

Verification is only claimed with evidence. The `pnpm verify` report is the
evidence for checks and obligations: paste it (or the CI job summary link)
into the PR. Add:

- screenshots for each `visual-check` item;
- your reading of the OpenAPI or lockfile diff when the report asks for it;
- explicitly what was skipped and why (a `--skip` reason, a waiver).

## Three axes

Every check sits somewhere on three axes. Local and CI verification differ
mainly in where they sit, not in tooling.

| Axis           | One end                                                                                                             | Other end                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Permanence** | _Throwaway_: written to convince yourself during a change, never committed (a scratch script, a curl, a screenshot) | _Kept_: committed to the suite and run forever as regression protection         |
| **Scope**      | _Targeted_: the code and flows the change touches                                                                   | _Complete_: the whole suite, as close to full coverage as is realistic          |
| **Realism**    | _Heuristic_: boundaries mocked or stubbed, dev servers, one browser                                                 | _Realistic_: production build, real dependencies and services, several browsers |

- **Local work** leans throwaway, targeted and heuristic: fast feedback while
  building.
- **CI and merge gates** lean kept, complete and realistic: proof nothing
  regressed.
- **Promote, don't accumulate.** When a throwaway check proves a behaviour
  that would be costly to break silently, turn it into a kept test. Otherwise
  let it go. Not every check belongs in the suite; suite bloat is a cost.

## Mocked vs real integration

Draw the line at what we control:

- **Never mock Postgres.** It runs in a throwaway Docker container and is
  fast. Most of the logic lives in SQL, so a fake database mainly tests the fake.
- **Mock what we don't control** in local and PR runs: Auth0 (sign test tokens
  with a local key), and the API when testing frontend components on their own.
- **Real integration** means the real Auth0 tenant, a deployed environment and
  the real network. It needs secrets, is slower and flakier, and runs only at
  the merge gate and after deploy.

## The agent visual check

A throwaway verification method used during development, required as manual
evidence for the `web-*` classes. It can be done by the coding agent or by a
person: change something, look at it, report what you saw. The `/verify`
skill (`.claude/skills/verify/SKILL.md`) walks through it.

| What you're checking                                                              | Tool                                                               |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| A static page, or one screen in a variant (mobile, dark mode)                     | Playwright CLI: `playwright screenshot`                            |
| A flow, or a state reached by interacting (typing an answer, finishing a session) | Throwaway spec in `apps/e2e/scratch/`, run with `pnpm e2e:scratch` |
| A flow worth guarding permanently                                                 | Promote the spec into `apps/e2e/tests/`                            |

**Steps:**

1. Run the app (`pnpm dev`), or let `pnpm e2e:scratch` start it.
2. **Static pages:**
   `pnpm --filter @app/e2e exec playwright screenshot --full-page <url> scratch/out/<name>.png`.
   Useful options: `--device "iPhone 15"`, `--color-scheme dark`,
   `--wait-for-selector <selector>`. The CLI only loads a URL; it can't click
   or type.
3. **Flows:** write a spec in `apps/e2e/scratch/`, which is git-ignored apart
   from its README. It uses the same fixtures and page objects as the real
   suite, so a flow is a few lines. It also saves screenshots wherever you
   point them (convention: `scratch/out/`), records a trace, and starts the
   servers if they aren't running. The scratch config is separate:
   `pnpm e2e` and CI never run these specs. Template: `apps/e2e/scratch/README.md`.
4. Collect console errors, and query the database or API if the change
   persists data.
5. Look at the screenshots and report what was checked, with the evidence.
6. **Promote or delete.** Move a scratch spec into `tests/` (screenshots
   replaced by assertions) only if it guards behaviour that would be costly to
   break silently.

## Stages

| #   | Stage                                          | Runs                                                                                                                                                                                           | Axes                                         | Target time |
| --- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------- |
| 0   | **Inner loop** (every edit)                    | Typecheck and unit tests for affected packages, editor formatting                                                                                                                              | targeted, heuristic, kept                    | seconds     |
| 1   | **Pre-commit** (`.githooks/pre-commit`)        | Biome on staged files                                                                                                                                                                          | targeted                                     | < 5 s       |
| 2   | **Local verify** (end of a task)               | `pnpm verify`: the checks, obligations and evidence list for the diff; `/verify` adds the visual check and throwaway checks. The pre-push hook re-checks obligations.                          | targeted, mostly heuristic, kept + throwaway | 1–2 min     |
| 3   | **CI on every PR push**                        | `pnpm verify --all` split over parallel jobs (static, database and tests, e2e on the production build), plus `obligations` and `commit-messages`. The `check` job is the single required gate. | complete, realistic-ish, kept                | < 5 min     |
| 4   | **Merge gate** (required checks / merge queue) | Cross-browser e2e (Chromium, Firefox, WebKit, mobile viewport); deploy a preview and run the real-integration smoke (real Auth0); migrations on a production-like data copy                    | complete, realistic                          | ~10 min     |
| 5   | **Post-deploy**                                | Smoke e2e against staging, then production; check the migration result                                                                                                                         | realistic                                    | minutes     |
| 6   | **Nightly**                                    | Flake hunting (each test repeated many times); full browser matrix; dependency audit; canary build on upcoming versions (Node 26, TypeScript 7, latest deps)                                   | complete                                     | unbounded   |
| 7   | **Production**                                 | Error tracking; a synthetic check of the study flow                                                                                                                                            | realistic                                    | continuous  |

Stages 4–5 need a deploy target; see [ADR 0001](adr/0001-dedicated-repository.md).

## Changing the rules

Edit `scripts/verify/rules.ts`, then `pnpm verify docs` and commit both.
`scripts/verify/plan.test.ts` pins how sample paths are classified and
asserts that every tracked file has a class, so a new top-level folder fails
the tests until someone decides what verifying it means.
